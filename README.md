# GUtv_backend_dotnet

## Сессии нескольких устройств (ветка `test`)

Каждый вход создаёт запись `UserSessions` с отдельным случайным refresh token.
В базе хранится только SHA-256 хеш токена. JWT содержит `sid`; middleware при
каждом авторизованном HTTP-запросе проверяет владельца, срок и отзыв сессии,
блокировку пользователя и его актуальную роль. Отзыв прекращает доступ с уже
выданным JWT при следующем запросе, без ожидания истечения JWT.

Обновление токенов атомарно меняет только свою сессию и сохраняет её `sid`.
Повторное использование старого refresh token отклоняется. Вход, обновление,
выход со всех устройств и блокировка согласованы транзакциями и блокировками
PostgreSQL. При разблокировке прежние сессии не восстанавливаются.

Срок сессии — семь дней с последнего входа/обновления, как в прежней схеме.
`LastUsedAt` обозначает последнее обновление токенов, а не каждый просмотр страницы.
Число одновременных сессий не ограничено. Название браузера/ОС в интерфейсе
определяется приблизительно по User-Agent; это не аппаратный идентификатор.

GraphQL сохраняет формат `login`, `register` и `refreshToken`. Добавлены:

- `mySessions`: только собственные активные сессии; поля `id`, `createdAt`,
  `lastUsedAt`, `expiresAt`, `userAgent`, `isCurrent`. Секреты не выдаются.
- `logout`: отзыв текущей сессии.
- `revokeMySession(sessionId: UUID!)`: отзыв только собственной выбранной сессии.
- `logoutAll`: отзыв всех текущих сессий пользователя, включая вызывающую.

Все операции управления сессиями требуют авторизации. Серверные сессии
отличаются от клиентского `auth_session_id`, который координирует вкладки.

### Миграция и совместимость

`20261003223350_AddUserSessions` создаёт таблицу и удаляет прежние одиночные
`Users.RefreshToken` и `Users.RefreshTokenExpiryTime`. Пользователи, бронирования
и оборудование сохраняются. Прежние JWT не имеют `sid` и будут отклонены:
после будущего применения миграции всем потребуется заново войти.
Откат сохраняет аккаунты, но не восстанавливает прежние токены/сессии.

Ветка `test` не запускает существующий deploy workflow: он разрешён только
для `master`. Само приложение применяет миграции при запуске, поэтому для
локальной проверки обязательно использовать отдельную тестовую БД.

### Проверки

```bash
dotnet test
GUTV_SESSION_TEST_POSTGRES='Host=127.0.0.1;Port=55438;Database=postgres;Username=gutv_session_test' dotnet test
dotnet publish GUtv_backend_dotnet.csproj -c Release -o /tmp/gutv-session-publish
```

Переменная должна указывать на локальный PostgreSQL, где тестовая роль имеет
право `CREATE DATABASE`. PostgreSQL-тесты создают БД со случайным именем
`gutv_session_test_*` и удаляют только созданную ими БД. Без переменной эти
интеграционные тесты явно пропускаются, остальные тесты выполняются.

Проверено 4 октября 2026: 174 теста, без ошибок и пропусков, включая девять
PostgreSQL/HTTP-тестов. Проверены миграция существующей БД, откат и повторное
применение, регистрация и неверный пароль, независимые входы/обновления,
повторное использование токена, конкурентные обновления и отзыв, запрет
доступа к чужим сессиям, блокировка/разблокировка и отсутствие секретов в схеме.
Release publish успешен. В старой миграции `rolefix` остаются два предупреждения
о названии типа; ошибок сборки нет.
